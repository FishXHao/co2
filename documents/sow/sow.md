## 1. 背景與目標

### 1.1 背景

需求方希望參考指定服務站點，規劃並開發一個具備相近服務體驗的網站。本專案現有登入系統可作為前後端分離、認證與容器化部署的技術基線，但現有文件尚未定義新網站的業務目的、頁面範圍、使用者角色或外部系統整合。

### 1.2 目標

1. 透過參考站點勘查，建立可核定的頁面、功能、角色與流程清單。
2. 產出可交付給 UIUX、SA、PG 與 QA 的需求、設計、技術與驗收文件。
3. 開發可在手機、平板與桌面使用的響應式網站。
4. 依核定範圍實作必要的前端、後端、認證與資料整合能力。
5. 建立可重複建置、測試、部署與交接的交付流程。

### 1.3 成功條件

- 需求方核准頁面清單、核心流程、角色權限與不納入範圍。
- 每個納入範圍的 User Story 都有可測試的驗收標準。
- 核心流程可在支援的手機、平板與桌面尺寸完成。
- 重大流程具備正常、載入、空白、錯誤、停用與成功狀態。
- QA 測試完成，UAT 不存在未接受的 Critical 或 High 缺陷。
- 原始碼、設定、測試報告、部署說明與操作交接文件完整交付。

## 2. 目標使用者與角色

依 P0 勘查，本網站為**公開資訊網站**，主要為資訊展示型，不涉及登入與受保護個人化服務。

| 角色 | 主要目標 | 主要需求 |
|------|----------|----------|
| 一般訪客（公眾） | 閱讀碳封存計畫資訊、瀏覽環境監測結果 | 清楚導航、響應式、無障礙介面、可讀的監測圖表 |
| 內容/業務管理者 | 維護網站內容與監測資料 | 內容更新流程、資料來源管理（後續階段確認） |
| 專案管理與維運人員 | 確認品質並維持服務 | 日誌、監控、部署、備份與故障處理 |

> 已登入使用者角色：**不納入**（P0 確認網站無登入需求）。若後續需求方要求加入登入/後台，需透過變更控管。

## 3. 工作範圍

### 3.1 P0 - 參考站點與需求勘查（必要）

- 確認參考站點可用性、登入方式、測試帳號與可提供的截圖/錄影。
- 建立路由與頁面盤點：公開頁、登入後頁、表單、列表、詳細頁、錯誤頁。
- 盤點使用者角色、權限、主要任務、流程分支與例外狀態。
- 確認文字、圖片、Logo、圖示及其他內容資產的授權與提供方式。
- 盤點 API、資料來源、SSO、第三方服務、檔案服務與通知服務。
- 確認非功能需求：瀏覽器、響應式尺寸、無障礙、SEO、效能、資安、日誌與可用性。
- 產出《參考站點勘查報告》、頁面清單、功能優先級與需求疑問清單。

**P0 通過條件**：需求方核准頁面/功能清單、核心流程、角色權限、外部整合清單與 MVP 邊界。

### 3.2 P1 - 需求與產品規格

- 將核定範圍拆解為 User Story、驗收標準、優先級與相依性。
- 建立 MVP、第二階段與不納入範圍。
- 定義內容維護責任、資料生命週期、錯誤處理與通知規則。
- 建立風險、未決決策、變更控管與 UAT 規則。

### 3.3 P2 - UX/UI 設計

- 資訊架構、網站地圖與導航規劃。
- 核心流程與例外流程設計。
- 低保真 Wireframe 與高保真視覺稿。
- 設計色彩、字體、間距、元件、狀態與響應式規格。
- 定義鍵盤操作、焦點、語意化標記、錯誤提示與色彩對比要求。
- 產出可交付給 PG 與 QA 的設計規格與 UI 驗收條件。

### 3.4 P3 - 前端網站開發

- 以 Vue 3 Composition API + Vite 建立網站頁面與共用元件。
- 實作核定的導航、頁面模板、表單、列表、詳細資訊與回饋狀態。
- 串接核定的 API 或外部服務。
- 實作登入、登出、Session/Token 狀態與權限導向（若 P0 確認需要）。
- 實作響應式版面、鍵盤操作、基本 SEO metadata 與載入/錯誤狀態。
- 不在未核定範圍內自行增加頁面、角色或商業流程。

### 3.5 P4 - 後端與資料整合

依 P0 確認，網站為公開資訊網站，MVP 監測圖表**先以前端 mock 資料展示**。後端 API 於後續階段建立，用於提供監測資料：

- 以 Node.js + Express 建立監測資料 RESTful API（大氣、地下水、地震、土壤氣體）。
- 輸入驗證、統一錯誤回應與安全標頭。
- 依核定資料模型整合 SQL Server、Redis 或既有外部 API。
- 更新 Swagger/OpenAPI 與資料庫 Schema 文件。
- 登入/認證/權限：**不納入**（P0 確認無此需求）。

### 3.6 P5 - QA、資安與驗收

- 依 User Story 建立測試案例與測試計畫。
- 執行功能、整合、API、E2E、響應式、瀏覽器相容性與無障礙測試。
- 依需求執行基本效能與安全性檢查。
- 記錄缺陷、重測、回歸測試與 UAT 結果。

### 3.7 P6 - 部署與交接

- 更新 Docker、Nginx、環境設定與部署流程。
- 建立開發、測試與正式環境的設定差異說明。
- 交付建置/部署 Runbook、操作說明、已知限制與維運交接資料。
- 完成需求方驗收與正式上線前檢查。

## 4. MVP 建議邊界

依 P0 勘查確認的**功能對等**範圍（已確認基準）：

- 1 個響應式網站外框與共用導航。
- 10 個盤點路由（詳見勘查報告），以公開資訊頁面為主。
- 5 種環境監測頁（大氣、地下水、地震、土壤氣體）以動態圖表呈現，**資料先以前端 mock 展示，後端 API 之後再串接**。
- 1 個無障礙規範（Accesskey 快捷鍵、四大區塊），遵循 WCAG 目標。
- 中文介面（zh-Hant-TW）；不需多語系。
- **不含登入/SSO/角色權限/管理後台**（P0 確認無此需求）。
- 不含既有內容大量搬遷、複雜報表、支付、行動 App 與未核定的第三方整合。

若參考站點勘查結果超出上述假設，需透過變更控管重新估算。

## 6. User Stories 與驗收標準

### US-SOW-001：完成參考站點勘查

**作為** 專案團隊  
**我想要** 取得參考站點的頁面、流程、角色與整合盤點  
**以便** 以已確認範圍估算與開發網站

**驗收標準**：

- [ ] 盤點所有納入本案的路由與頁面模板。
- [ ] 每個核心流程標示起點、操作步驟、成功、失敗與例外結果。
- [ ] 每個頁面標示使用者角色、資料來源與權限需求。
- [ ] 外部 API、SSO、檔案、通知與第三方服務均標示已知狀態。
- [ ] 需求方核准盤點結果與 MVP 範圍。

**優先級**: P0  
**預估工時**: 24-40 小時

### US-SOW-002：瀏覽核定的公開內容

**作為** 訪客  
**我想要** 透過導航進入核定的公開頁面並閱讀內容  
**以便** 找到需要的資訊或服務入口

**驗收標準**：

- [ ] 所有核定公開路由可由導航或明確連結抵達。
- [ ] 目前位置與頁面標題清楚可辨識。
- [ ] 桌面、平板與手機版均可閱讀且無水平溢出。
- [ ] 內容載入失敗時顯示可理解的錯誤狀態與後續操作。
- [ ] 鍵盤使用者可完成導航，焦點順序合理且清楚可見。

**優先級**: P1  
**預估工時**: 32-56 小時，依頁面數調整

### US-SOW-003：完成核心服務流程

**作為** 核定的目標使用者  
**我想要** 完成一項核心服務流程並取得結果  
**以便** 達成網站主要業務目的

**驗收標準**：

- [ ] P0 產出的流程圖已標示所有必要輸入、驗證與權限。
- [ ] 必填欄位、格式錯誤與邊界值有明確提示。
- [ ] 送出期間禁止重複操作並提供處理中的回饋。
- [ ] 成功結果、失敗原因、網路錯誤與伺服器錯誤均有對應狀態。
- [ ] QA 可依測試案例重複完成流程並驗證結果。

**優先級**: P1  
**預估工時**: 40-80 小時，依流程與整合數調整

### US-SOW-004：安全登入與個人化服務（不納入）

**作為** 已註冊使用者  
**我想要** 安全登入並使用受保護功能  
**以便** 查看或操作與我相關的服務資料

**狀態**：**不納入**（P0 確認本網站為公開資訊網站，無登入需求）。若後續需求方要求加入登入、SSO、角色權限或個人化服務，需透過變更控管重新評估，並重新制定認證與授權驗收標準。

### US-SOW-005：完成品質驗收與交接

**作為** 需求方與維運人員  
**我想要** 取得可驗證、可部署與可維護的網站交付物  
**以便** 進行 UAT、上線與後續維運

**驗收標準**：

- [ ] 所有 P0/P1 User Story 有測試案例與執行結果。
- [ ] UAT 核心流程通過，Critical/High 缺陷已修復或由需求方書面接受。
- [ ] 建置、測試與部署步驟可依 Runbook 重複執行。
- [ ] 設定、帳號、密鑰與環境差異已以安全方式交接。
- [ ] 已知限制、剩餘風險與後續 Backlog 已列明。

**優先級**: P0  
**預估工時**: 40-64 小時

## 8. 不納入範圍

除非另行核准，本 SOW 不包含：

- 參考站點未公開或未提供的功能推測與完整複製。
- 未取得授權的 Logo、圖片、文字、程式碼或其他內容資產。
- 大量歷史資料清理、資料移轉與人工內容建置。
- 原生 iOS/Android App、桌面 App 或離線功能。
- 支付、電子簽章、複雜審批、即時通訊或大量報表。
- 未在 P0 確認的 SSO、第三方 API、CMS、後台與多語系。
- 正式環境主機、憑證、網路白名單、資安稽核或第三方服務費用。

## 9. 依賴與前置條件

- 需求方提供參考站點可合法使用的測試帳號、操作權限或足夠的截圖/錄影。
- 需求方提供品牌規範、內容、圖片、Logo、圖示與授權證明。
- 需求方確認目標使用者、核心業務目標、頁面清單與優先級。
- SA 確認 API、資料庫、SSO、外部服務、部署環境與資安要求。
- PG 取得開發、測試、資料庫與部署環境的必要權限。
- QA 取得測試資料、測試帳號、瀏覽器/裝置矩陣與驗收窗口。
- 正式上線需有主機、網域、TLS 憑證、DNS、監控與備份責任人。

## 10. 風險與處理方式

| 風險 | 影響 | 機率 | 處理方式 |
|------|------|------|----------|
| 參考站點無法存取或需要授權 | 無法完成頁面/流程盤點 | 高 | P0 前取得合法帳號、截圖、錄影或需求方示範 |
| 參考站點功能與表面頁面不一致 | 估算漏項與返工 | 高 | 以操作流程、角色與 API 盤點作為需求基線 |
| 內容/資產授權不明 | 無法合法上線 | 中 | 由需求方提供授權或改用自有內容 |
| 外部 API/SSO 文件不足 | 整合延誤 | 中 | P0 建立整合清單與 mock 契約，未確認項目不納入 MVP |
| 頁面數與流程持續增加 | 時程與成本超出 | 高 | 建立變更申請，新增範圍重新估算 |
| 個資與認證要求晚期才提出 | 架構返工與資安風險 | 中 | SA 在 M0/M1 完成資料分類、權限與認證設計 |
| 瀏覽器、裝置或效能要求未定義 | 驗收爭議 | 中 | P1 核准支援矩陣與量測基準 |

## 11. 未決問題

依 P0 勘查，以下問題已獲得初步確認；其餘仍待需求方最終核准：

已確認：
1. 主要業務目的：公開碳封存計畫資訊與環境監測結果展示。
2. 需求：**功能對等**（實作盤點頁面，含動態監測圖表）。
3. 盤點頁面：詳見勘查報告，共 10 個路由。
4. 登入/SSO/角色權限/個人化/後台：**不納入**。
5. 既有 API/資料庫：MVP 採前端 mock 資料，後端 API 之後串接。
6. 內容來源：以參考站點公開內容為基準，正式上線需取得授權。
7. 多語系：不需；SEO/無障礙：需要（Accesskey、WCAG）。

仍待確認：
8. 目標瀏覽器、裝置矩陣、無障礙等級、效能指標與資安標準的正式核定。
9. 正式部署環境、網域、TLS、監控、備份與維運責任由誰負責。
10. 預算、上線日期、UAT 窗口與變更審批人是誰。

## 12. 變更控管

下列變更需重新評估工時、時程與交付物：

- 新增頁面、角色、核心流程或外部整合。
- 變更既定 API、資料模型、認證方式或部署環境。
- 增加多語系、CMS、支付、報表、行動 App 或大量資料移轉。
- 改變瀏覽器/裝置支援矩陣、效能目標或資安驗收標準。
- 參考站點勘查後發現原估算基準不適用。

- `documents/sd-docs/architecture.md`：確認新網站是否沿用現有登入系統架構。
- `documents/sd-docs/technical-spec.md`：補充核定的整合、資安、效能與部署要求。
- `documents/sd-docs/design-decisions.md`：記錄新架構或技術選型 ADR。
- `documents/api-docs/swagger.json`：新增或調整 API 契約。
- `documents/db-schema/`：需要持久化資料時更新 Schema 與 ER 圖。
- `documents/event-storming/`：新增核心業務流程與領域事件。
- `documents/test-case/`：建立前端、後端、整合與 UAT 測試案例。

### 協作角色

- **PM**：主持 P0、建立需求基線、管理範圍/優先級/變更與驗收窗口。
- **SA**：確認架構、API、資料、資安、效能、整合與技術風險。
- **UIUX**：完成資訊架構、流程、視覺稿、響應式與無障礙規格。
- **PG**：評估實作可行性、開發前後端、串接服務與部署資產。
- **QA**：建立測試策略、執行驗證、管理缺陷與支援 UAT。
- **需求方/業務代表**：提供參考站點資訊、內容資產、決策與最終核准。

## 14. 建議下一步

1. 由需求方提供參考站點的可操作帳號、頁面截圖/錄影或功能清單。
2. 安排 60-90 分鐘 P0 勘查工作坊，確認角色、核心流程與 MVP。
3. PM 依 P0 結果建立 `requirements.md` 與前/後端 User Stories。
4. SA、UIUX、PG、QA 共同審查 P0 產出並修正工時與里程碑。
5. 需求方核准 SOW v1.0 後，才進入設計與開發排程。
