> 本 WBS 是規劃級工作分解，範圍、工時與任務依賴必須在 P0 參考站點勘查及需求方核准後更新。未確認的登入、CMS、SSO、第三方 API、資料移轉與多語系工作均視為條件式任務。

## 1. WBS 使用方式

### 1.1 分解原則

- 以可交付物與可驗收結果拆分，不以單純技術活動作為唯一分界。
- 每個末端任務應有負責角色、前置依賴、工時範圍與完成條件。
- 未核定的功能不得直接排入基準範圍；以 `C` 標示條件式任務。
- 工時為人時，不等同日曆工期；等待帳號、內容、審批、環境與外部服務的時間另計。
- 變更頁面、角色、流程、整合或非功能需求時，必須回到 SOW 進行影響評估。

### 1.2 角色代碼

| 代碼 | 角色 |
|------|------|
| PM | Project Manager，專案經理 |
| SA | System Analyst，系統分析師 |
| UX | UI/UX Designer，介面與體驗設計師 |
| PG | Programmer，程式設計師 |
| QA | Quality Assurance，測試工程師 |
| BA | 需求方/業務代表 |
| OPS | 維運或基礎設施負責人 |

### 1.3 狀態與優先級

- **狀態**：`Not Started`、`In Progress`、`Blocked`、`Ready for Review`、`Accepted`。
- **優先級**：`P0` 必要前置或驗收工作、`P1` MVP 核心、`P2` 次要或可延後、`C` 條件式範圍。
- **工時**：以 `min-max h` 表示規劃級人時範圍。

```text
1.0 專案治理
    |
    v
2.0 P0 勘查與範圍確認
    |
    v
3.0 P1 需求與技術基線
    |
    v
4.0 P2 UX/UI 設計核准
    |--------------------|
    v                    v
5.0 P3 前端開發       6.0 P4 後端/資料整合
    |--------------------|
             v
      7.0 P5 QA/UAT
             |
             v
      8.0 P6 部署/交接
```

**關鍵依賴**：

- 2.0 未完成且未獲 BA 核准前，不可凍結頁面、角色、流程與估算。
- 3.0 未完成前，不可將未確認的功能直接交付開發。
- 4.0 設計核准後，5.0 與 6.0 可並行，但 API 契約與核心流程需同步確認。
- 7.0 必須在 5.0、6.0 的 MVP 功能完成並部署至測試環境後開始正式驗證。
- 8.0 必須在 QA/UAT 通過、缺陷處置與上線責任確認後執行。

## 7. 目前需先確認的 WBS 變數

以下變數未確認前，WBS 只能作為規劃基線：

1. 參考站點是否可提供合法測試帳號、截圖或操作錄影。
2. MVP 實際頁面數是否超過 12 個路由與 4-6 種模板。
3. 是否納入登入、SSO、角色權限、管理後台與個人化服務。
4. 是否需要 SQL Server、Redis、既有 API 或其他第三方整合。
5. 是否需要內容搬遷、CMS、多語系、搜尋、報表、通知或檔案上傳。
6. 支援瀏覽器、裝置、WCAG 等級、效能與資安量測基準。
7. 正式環境、DNS、TLS、監控、備份、維運與上線審批責任人。
8. 預算、上線日期、UAT 窗口及需求變更的核准流程。

## 8. WBS 變更規則

- P0 核准前：允許調整任務結構與估算，不視為基準變更。
- P0 核准後：新增或刪除 WBS 末端任務，需記錄範圍、工時、時程與風險影響。
- G2 後：變更 User Story、驗收標準、角色、核心流程或外部整合，需由 PM/SA/QA/BA 共同評估。
- G3 後：變更 UI、API、資料模型或部署方式，需建立技術/設計決策紀錄。
- G5 後：只接受不影響已驗收核心流程的修正；其餘列入後續版本或重新排程。
